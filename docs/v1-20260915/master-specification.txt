============================================================
1. PRODUCT DEFINITION
============================================================

Zylora is an AI-assisted website builder and business-conversion platform.

A user should be able to:

1. Sign in.
2. Click Create Website.
3. Enter the canonical Zylora Studio.
4. Start from a clean blank website canvas.
5. Add sections and visual elements.
6. Move, resize, overlap, align, group, layer, style, and edit elements.
7. Build multiple pages.
8. Link buttons and navigation items to pages, anchors, external URLs, phone numbers, email addresses, and appointment flows.
9. Bind supported elements to CMS data.
10. Add lead forms.
11. Add appointment/calendar experiences.
12. Add and customize the AI Sales Assistant/chatbot.
13. Use AI inside the editor to make selected-element, selected-section, page-level, or site-level changes.
14. Preview the website responsively.
15. Configure SEO and site settings.
16. Publish using the existing Zylora publishing authority.
17. Receive leads and appointments in the user dashboard.
18. Receive configured email and/or WhatsApp notifications.
19. Manage credits, plan, billing, sites, leads, appointments, analytics, integrations, and account settings.
20. Reopen the same site later and see exactly the same editable document state.

The product must feel cohesive.
The Studio must not feel like one application while the dashboard, publisher, CMS, and AI feel like unrelated systems.

============================================================
2. GOVERNING PRODUCT DECISIONS
============================================================

Treat the following as the current governing decisions unless the existing codebase contains a newer explicitly documented decision that clearly supersedes one of them.

2.1 Website creation
--------------------
- The main creation path is blank-canvas-first.
- The user clicks Create Website.
- The app creates a real site/document record.
- The user is routed to the canonical Studio route:
  /studio/{site_id}
- A clean initial page exists.
- A plain starter section may exist so the user is not staring at a technically empty document.
- There must NOT be a mandatory template-selection step.
- There must NOT be a mandatory "Create with AI" screen before the editor opens.
- AI remains available INSIDE the Studio after the user is in the editor.

2.2 Templates
-------------
The current product direction is to remove the old template catalogue from the primary user creation workflow.

If legacy template routes, assets, seeds, APIs, UI links, thumbnail systems, template-specific publishing branches, or obsolete tests remain, audit them.

Do one of the following based on the actual repository:
- Remove obsolete template functionality cleanly where it is no longer part of the product.
- Preserve only the minimal compatibility code that is still required to open existing customer documents safely.

Do not leave half-dead template features exposed to users.

User-created reusable designs may be supported separately later or as an explicit "Save as reusable design" capability. Do not reintroduce the old catalogue merely to satisfy old code.

2.3 Page limit
--------------
The intended upper bound is 298 pages per website for all primary plans unless a newer repository-level product constant explicitly overrides it.

The page limit must be enforced server-side.
Frontend-only enforcement is insufficient.

Test:
- create page
- duplicate page
- delete page
- restore/recreate near limit
- publish near limit
- page count after failed request
- concurrent create requests

2.4 Free branding
-----------------
Free published websites must display "Built with Zylora" branding.

Paid websites must not display Zylora branding simply because they use a Zylora subdomain.

Branding state must be server-authoritative and based on current entitlement.

2.5 Plans and regional pricing
------------------------------
Current plan structure:
- Free
- Starter
- Growth
- Pro / Get in Touch where applicable

Current regional prices:
India:
- Starter: ₹799/month
- Growth: ₹1,799/month

International:
- Starter: US$9/month
- Growth: US$19/month

The final billed amount/currency/entitlement must never be trusted from client-side values.

2.6 AI credits
--------------
AI credits are the common usage wallet for customer-triggered AI features unless a more recent unified-credit implementation in the repository already defines the exact accounting model.

Every AI path must route through one accounting boundary.

No hidden unmetered paths.
No frontend-calculated final charge.
No AI call should accidentally bypass reservations/settlement if the repository already implements that system.

2.7 Lead/messaging credits
--------------------------
Lead notification usage must follow the latest configured business rule in the backend.

The expected product behavior is:
- sending an email notification consumes the configured messaging/lead credit cost
- sending a WhatsApp notification consumes the configured messaging/lead credit cost
- retries must not double-charge
- failed delivery must follow the existing settlement/refund policy
- the same lead event must not create duplicate billing due to webhook or worker retry

Use server-side idempotency.

2.8 Session behavior
--------------------
Navigating backward/forward in the browser must not effectively log the user out.

Session state persists until:
- explicit logout
- token/session expiry
- security revocation
- account-level invalidation

Do not couple navigation history to authentication state.

3. NON-NEGOTIABLE ARCHITECTURAL RULE
============================================================

ZYLORA MUST HAVE ONE SOURCE OF TRUTH FOR THE EDITABLE WEBSITE.

That source of truth is the Zylora SiteDocument (or the existing canonical equivalent already used by the repository).

Do not create:
- Penpot/editor projection state as one truth
- Studio state as another truth
- rendered DOM as another truth
- AI state as another truth
- CMS binding state as another truth

All editor surfaces must read/write through the same canonical document model.

The target dependency direction is:

UI
  ↓
Commands / Mutations
  ↓
SiteDocument
  ↓
History / Autosave / AI / CMS bindings
  ↓
Renderer
  ↓
Preview / Publish

Every mutation must be serializable.
Every important mutation must be undoable unless it is explicitly non-document state.
Every persisted mutation must survive reopen.
Every published result must be derivable from the canonical saved document.

4. PENPOT-BASED STUDIO INTEGRATION STRATEGY
============================================================

PENPOT is the governing open-source editor/design foundation for Zylora Studio.

This is not a request to merely make the Studio "look like Penpot".
Use Penpot's proven interaction and design-system concepts, and where technically appropriate its open-source implementation, to power the editor surface.

However, Zylora must remain one coherent product.

4.1 Non-negotiable architecture
-------------------------------
Do NOT:
- iframe `design.penpot.app`
- redirect users into a separate Penpot product
- expose Penpot branding as the user-facing editor identity
- create a second authoritative Penpot database for website state
- make a Penpot file and SiteDocument compete as independent sources of truth
- create a second undo stack that can diverge from Zylora history
- create a second page model
- create a second responsive model
- create a second media ownership model
- bypass Zylora authentication, tenancy, billing, AI accounting, CMS, forms, appointments, renderer, preview, or publish
- publish raw Penpot HTML/CSS as an uncontrolled alternate publishing path

Zylora SiteDocument remains the canonical persisted website/business document.

Required dependency direction:

ZYLORA STUDIO UI
  ↓
PENPOT-DERIVED DESIGN / INTERACTION ADAPTER
  ↓
ZYLORA COMMAND / MUTATION ENGINE
  ↓
CANONICAL ZYLORA SITEdocument
  ↓
HISTORY / AUTOSAVE / AI / CMS / BUSINESS BINDINGS
  ↓
ZYLORA RENDERER
  ↓
PREVIEW / PUBLISH

If Penpot internals require a scene representation:
- it is a projection/view model of the canonical SiteDocument;
- use stable one-to-one node identity mapping wherever possible;
- never persist a divergent hidden document as a second truth;
- regenerate/reconcile safely from canonical data;
- commit user changes through Zylora commands;
- validate every conversion at the adapter boundary.

DEFINITION

A "real icon" is:
- a genuine SVG/PNG/vector/raster asset distributed by the official third-party brand;
- OR a genuine glyph from Zylora's selected production SVG icon library;
- OR the exact reusable icon system shipped in the supplied dashboard ZIP where licensing permits.

A "real icon" is NOT:
- emoji;
- Unicode pictograms;
- a typed letter inside a circle pretending to be an app logo;
- a CSS recreation of a third-party trademark;
- an AI-generated imitation of a logo;
- a screenshot crop;
- an unofficial random logo downloaded from an aggregation website when a first-party asset exists;
- a broken-image fallback.

GENERAL ZYLORA ICONS

1. Inspect `free-react-tailwind-admin-dashboard-main.zip`.
2. Reuse its icon language/system when legally and technically appropriate.
3. If another icon library is needed, use ONE coherent licensed SVG icon family.
4. Avoid mixing multiple visually incompatible icon libraries.
5. Maintain consistent:
   - stroke/fill treatment;
   - optical weight;
   - bounding box;
   - control size;
   - vertical alignment;
   - hover/focus/disabled states.
6. Do not use emoji as navigation/action icons.
7. Every icon-only button must have:
   - accessible name;
   - tooltip where useful;
   - keyboard focus state.
8. Decorative duplicate icons should be hidden from assistive technology where appropriate.

THIRD-PARTY AI / APP LOGOS

For every branded integration:

1. Retrieve the CURRENT logo/icon from an official first-party source such as:
   - official brand center;
   - official media/press kit;
   - official developer documentation;
   - official product asset package.

2. Verify:
   - current mark;
   - suitable variant;
   - light/dark treatment;
   - allowed usage;
   - retrieval date.

3. Preserve:
   - aspect ratio;
   - official shape;
   - clear space where required;
   - approved color/monochrome variant;
   - legibility.

4. Do NOT:
   - stretch;
   - distort;
   - recolor arbitrarily;
   - redraw;
   - add gradients/glows to trademarks unless officially permitted;
   - imply sponsorship, partnership or endorsement;
   - place a logo under "Verified" unless the integration is actually verified.

5. If an official suitable asset cannot be used:
   - show provider/client name as text;

93. UNIVERSAL AI / AGENT INTEGRATION PLATFORM
============================================================

Zylora must implement a vendor-neutral Universal AI / Agent Integration Platform so that a customer can safely create, inspect, edit, analyze, preview, and—where explicitly authorized—publish Zylora websites from ANY current or future AI application that exposes a compatible external-tool mechanism such as MCP, authenticated APIs, function/tool calling, plugins, actions, connectors, extensions, SDK integration, or an equivalent supported mechanism.

The architecture MUST NOT depend on a fixed list of AI vendors.

The intended user experience is:

User connects Zylora to an AI client
  ↓
User speaks naturally in that AI client
  ↓
The AI discovers authorized Zylora tools
  ↓
The AI creates/updates the user's real Zylora site
  ↓
Changes are committed through Zylora's command/mutation boundary
  ↓
The same canonical SiteDocument opens in Zylora Studio
  ↓
The user may continue editing manually, with Zylora AI, or from another authorized AI client
  ↓
Preview/publish remain governed by Zylora

Example supported interaction:

"Create a premium website for my dental clinic in Chennai.
Use Home, Services, Doctors, About, Appointments and Contact.
Add appointment booking and the AI Sales Assistant.
Optimize the pages for local SEO.
Do not publish until I approve it."

The external AI should be able to complete the permitted draft-building workflow without bypassing Zylora's existing architecture.

93.1 Protocol strategy
----------------------

Build ONE vendor-neutral Zylora integration layer.

Primary integration surface:
- standards-compatible remote MCP server;
- authenticated HTTPS transport;
- production-grade authorization;
- structured tool schemas;
- stable tool names;
- predictable error contracts;
- versioned capability discovery;
- rate limiting;
- audit logging.

Compatibility surfaces MUST use the SAME Zylora Tool Service:
- Remote MCP;
- REST + OpenAPI;
- function/tool-calling schemas when a client requires them;
- action/plugin/connector adapters when a specific platform requires them;
- SDK wrappers only as thin clients over the same public/internal contract;
- automation/agent-platform adapters where legitimately supported.

NON-NEGOTIABLE:
- no duplicate business logic;
- no MCP-only hidden mutation path;
- no REST-only alternate SiteDocument semantics;
- no vendor-specific alternate document model;
- no vendor-specific billing/authorization bypass;
- no client adapter may write directly to the database.

Protocol priority:
1. MCP when the client supports compatible remote MCP.
2. Authenticated REST/OpenAPI when MCP is unavailable but API/tool actions are supported.
3. Thin client-specific adapter over the SAME Tool Service when required.
4. If an AI application exposes no usable external integration mechanism, mark it NOT_CURRENTLY_CONNECTABLE instead of faking support.

Do NOT create independent business logic for:
- ChatGPT
- OpenAI API clients
- Claude
- Manus
- future AI clients

Client-specific adapters or setup instructions may differ.
The authoritative Zylora tools and policies must not.

Target model:

ANY COMPATIBLE AI ASSISTANT / AGENT / AUTOMATION PLATFORM
        ↓
MCP | REST/OPENAPI | TOOL/FUNCTION CALLING | THIN CLIENT ADAPTER
        ↓
ZYLORA UNIVERSAL AGENT GATEWAY
        ↓
OAUTH / TOKEN / SCOPE / SITE-ALLOWLIST ENFORCEMENT
        ↓
ZYLORA TOOL SERVICE
        ↓
COMMAND / MUTATION ENGINE
        ↓
CANONICAL ZYLORA SITEdocument
        ↓
HISTORY / AUTOSAVE / VERSIONING
        ↓
PENPOT-DERIVED STUDIO PROJECTION
        ↓
RENDERER
        ↓
PREVIEW / PUBLISH

Do not bind the core architecture to one vendor's current UI terminology.
Provider-specific connection instructions may change without requiring a redesign of the Zylora platform.

93.9 Patch validation
---------------------

Before applying an external patch:

1. authenticate connector;
2. verify scope;
3. verify site ownership/allowlist;
4. verify current revision;
5. validate operation schema;
6. validate referenced node/page/media/CMS IDs;
7. validate parent-child hierarchy;
8. validate page/node limits;
9. validate URL schemes;
10. validate media ownership;
11. validate component constraints;
12. validate responsive property types;
13. validate system-node restrictions;
14. validate plan/entitlement where applicable;
15. calculate any Zylora-side usage cost if applicable;
16. execute transactionally;
17. create history/version/audit records;
18. persist;
19. return new revision + concise result.

If any operation in an atomic patch fails:
- default to rejecting the entire atomic patch;
- do not leave a half-mutated document;
- return actionable structured errors.

If partial/best-effort mode is ever supported:
- it must be explicit;
- every successful/failed operation must be reported;
- it must never be the silent default for critical document edits.

93.10 Optimistic concurrency
----------------------------

External agents can race with:
- Zylora Studio edits;
- Zylora AI edits;
- another connected AI client;
- another browser tab.

Every write should therefore use revision-aware mutation.

Expected behavior:
- tool reads revision N;
- tool submits patch against N;
- if server is still N, commit → N+1;
- if server moved to another revision, reject with STALE_REVISION unless safe automatic merge is explicitly proven;
- return the latest revision/context required for retry.

Do not silently overwrite newer human work.

93.11 Idempotency
-----------------

Every create/mutation operation that can be retried must support idempotency.

Especially:
- create_site;
- create_page;
- upload initiation;
- CMS upsert;
- apply_site_patch;
- publish;
- lead/appointment mutations where exposed.

Network/client retries must not:
- create duplicate sites;
- create duplicate pages;
- duplicate CMS entries;
- charge twice;
- publish twice in conflicting ways.

93.15 External AI and Zylora AI credits
---------------------------------------

B. Zylora infrastructure/tool execution cost;

- do not automatically charge Zylora AI credits merely because an MCP tool was called unless current product policy explicitly defines a tool/operation cost;
- Zylora-hosted AI calls triggered by the tool may consume Zylora AI credits according to the unified accounting policy.

Examples:

- no provider model call by Zylora;
- normally no Zylora AI inference charge;
